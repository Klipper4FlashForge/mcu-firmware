# FlashForge MCU firmware: recovered source

The Creator 5 / 5 Pro has four motion-control MCUs behind its MIPS host,
and all four run **Klipper MCU firmware** — FlashForge says so themselves,
in the `license: GNU GPLv3` field their own images carry. They ship the
images and not the source.

This repository recovers that source, one board at a time, to the standard
that leaves no room for argument: **the rebuilt image is byte-identical to
the one FlashForge ships.**

| board | MCU | clock | load addr | image | status |
|---|---|---|---:|---:|---|
| [levelBoard](mcu/levelBoard/) | N32G45x (reports `stm32f103xe`) | 128 MHz | `0x08004000` | 26,704 B | **byte-identical — done** |
| [eBoard](mcu/eBoard/) | `stm32f103xe` | 144 MHz | `0x08010000` | 43,580 B | not started |
| [heaterBoard](mcu/heaterBoard/) | `stm32f103xe` | 144 MHz | `0x08010000` | 34,748 B | not started |
| [mainBoardGD](mcu/mainBoardGD/) | `gd32h757zg` | 600 MHz | `0x08000000` | 45,552 B | not started |

## The levelBoard result

`klipper/` is unmodified upstream Klipper at `6d70050` plus **exactly one
commit**, the recovery itself. Built with the pinned toolchain it
reproduces `mcu/levelBoard/stock/levelBoard.bin` exactly:

| gate | result |
|---|---|
| MD5, ours and stock | `156366b40ccc51f5768e083fa8ead210` |
| size | 26,704 B both |
| `cmp -l` differing bytes | **0** |
| functions at stock's own address | 247 / 247 |
| instructions identical | 7,093 / 7,093 (100 %) |
| command handlers identical | 54 / 54 |
| data dictionary, identify blob | match |

Not a lookalike and not a functional equivalent — the same 26,704 bytes.

## Verifying it yourself

    ./test/verify.sh

It refuses to run while `klipper/` has uncommitted edits, so a pass is a
statement about the committed source and not about whatever happens to be
in the working tree. Then it fetches the pinned GCC ARM 10.3-2021.10
toolchain and builds classic zlib, builds, and fails on the first gate that
does not hold. It needs `curl`, `git`, `python3` and a host C toolchain for
the zlib build, and roughly 600 MB in `work/`.

`./build.sh` is the build alone, without the comparison gates.

Three things have to be pinned before any of this is reproducible at all,
and `build.sh` pins all three: the version stamp Klipper bakes into the
embedded dictionary, the exact compiler named by the image's own
`build_versions`, and classic zlib (Fedora's Python links zlib-ng, whose
deflate output differs byte for byte at the same level).

### Why a commit and not a patch

    git log --oneline klipper/
    c1ae36d Recover the FlashForge levelBoard firmware, byte for byte
    9c72499 Import upstream Klipper 6d70050, unmodified

The first commit's tree hashes to upstream's own tree object
(`0122efca6c0ad8c754982094ce2eb7cf88fe906f`), so the baseline is provably
unedited and the second commit can be lifted onto a real Klipper fork:

    git format-patch -1 --relative=klipper -o /tmp <recovery-sha>
    git -C <your-klipper-fork> checkout -b flashforge 6d70050
    git -C <your-klipper-fork> am /tmp/0001-*.patch

From there it rebases onto any later upstream like ordinary work. That is
what a patch file in a directory could never give you: real history, real
blame, and a diff `git` computes rather than one somebody regenerated by
hand and hoped was current.

## Continuing on another board

Read [`.claude/skills/mcu-recovery/SKILL.md`](.claude/skills/mcu-recovery/SKILL.md)
first — it is the map: what the levelBoard job settled and must not be
re-opened, the compiler lever that closed its hard functions, and where the
other three boards start. Then the `mcu-board-bootstrap` agent takes an
image from "a `.hex` in the control component" to a tree with layout
pinned, before any function matching begins.

The eBoard and heaterBoard are the near targets: same MCU family, same
toolchain, and everything pinned about GCC 10's behaviour transfers
directly. `mainBoardGD` needs a GD32H7 port that upstream does not have.
